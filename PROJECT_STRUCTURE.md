## Database Schema

### Tables

| Table | Purpose |
|-------|---------|
| `user_profiles` | User info, macros targets, goals, streaks |
| `food_logs` | Daily food entries per user |
| `water_logs` | Daily water intake (one row per user per day) |
| `weight_entries` | Weight log with optional progress photo |
| `workout_logs` | Workout sessions with exercises JSON |
| `workout_plans` | AI-generated workout plans (JSON) |
| `saved_meals` | User-saved meal presets |

### Functions

| Function | Description |
|----------|-------------|
| `get_leaderboard_stats(start_date text)` | Leaderboard aggregation (STABLE) |
| `get_leaderboard_stats(start_date date)` | Leaderboard aggregation (SECURITY DEFINER) |

### RLS

All tables have RLS enabled. Users can only read/write their own rows via `auth.uid() = user_id`.

### Storage

| Bucket | Access | Path format |
|--------|--------|-------------|
| `weight-photos` | Public read, authenticated write | `{user_id}/{timestamp}.{ext}` |

## Key Architectural Notes

- **SSR**: TanStack Start provides SSR. Server routes and client routes share the same file via `createServerFn`.
- **Auth**: Supabase Auth with session cookies managed by `auth-middleware.ts`. The `useAuth()` hook exposes the current user.
- **Storage**: All photo operations route through `src/services/storage.ts`. Components never call `supabase.storage` directly.
- **AI**: Groq API is called server-side via `src/server/groq.ts`, exposed through `createServerFn` in `src/server/ai.ts`. Multiple keys are round-robined for rate limit handling. Client code never touches the Groq API key.
- **Food DB**: three bundled files are merged into one `ITEMS` array by `src/lib/foodDb.ts` and searched client-side for instant offline results — `ifct2017.json`, `extraFoods.ts`, and `restaurantFoods.json`. Energy is stored in **kilojoules** throughout; `kcal()` converts on read.

- **`ifct2017.json` is not the IFCT 2017 dataset, despite the name.** It holds 1556 rows: only 542 are real IFCT (single-letter codes `A`–`T`), and the other 1014 are a previously-merged manual corpus — `ASC*`/`asc_manual` (490), `BFP*`/`bfp_manual` (376), `OSR*`/`open_source_recipes` (148). Anyone handed a "new" food dump should check for overlap against those before importing: the `food data.txt` supplied in Aug 2026 turned out to be **already fully present** here (all 1004 rows matched by name, with identical macros and the kJ conversion already applied). Re-importing it would have created 1004 duplicates.

- **Restaurant menu data**: `restaurantFoods.json` is generated, never hand-edited. Re-build with `node scripts/build-restaurant-foods.mjs <dir>` pointed at the `data/` directory extracted from `zenin-nutrition-scraper-main.zip` (the zip itself is ~34MB of the scraper's `node_modules` and is not committed). The script's header documents the four incompatible source shapes, the serving-weight estimation, and the data repairs; `scripts/build-restaurant-foods.test.mjs` covers the logic. Menu rows carry `serving_g`/`serving_label`, which is what makes the food dialog open at "1 burger" instead of 100 g.

- **Known data debt**: across the already-merged manual rows the kJ conversion is slightly inconsistent — the energy ratio against the original kcal source has a median of 4.1736 but ranges 3.401 to 4.292. Not corrected; recorded so it is not rediscovered.
- **Barcode**: ZXing library handles barcode scanning; fallback to Open Food Facts API for nutrition lookup.
- **Routing**: TanStack Router auto-generates `routeTree.gen.ts` — do not edit manually.
